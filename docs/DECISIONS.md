# DECISIONS — Журнал принятых решений

> Сюда записываем ВАЖНЫЕ выборы и причину. Чтобы не переобсуждать одно и то же.
> Claude добавляет запись, когда принимается значимое архитектурное/продуктовое решение.

Формат: дата — решение — почему.

---

- **(старт)** — Платформа: VK Mini App — потому что аудитория реселлеров уже в ВК.
- **(старт)** — Без оплат/сделок внутри, только сведение контактов — упрощает MVP и снимает юридические риски.
- **(старт)** — Продавцы только после ручной модерации — защита от кидал, критично для реселла.
- **(старт)** — Стек React+TS / Fastify+TS / PostgreSQL+Prisma — популярный стек, ИИ генерит увереннее, один язык на проект.
- **(старт)** — Единый справочник брендов/моделей с автоподстановкой — иначе поиск разваливается из-за разнобоя в написании.
- **(старт)** — Память проекта в .md внутри репозитория = волт Obsidian — Claude Code читает файлы проекта, отдельный волт он не видит.
- **2026-06-28 (Фаза 1)** — Монорепо на npm workspaces (`frontend` + `backend`), Prisma-схема в корневой `prisma/` — один `npm install` ставит всё, общий корень для скриптов и БД.
- **2026-06-28 (Фаза 1)** — Связь фронт↔бэк в dev через прокси Vite (`/health` → `:3000`), а не CORS — меньше зависимостей и настроек на старте.
- **2026-06-28 (Фаза 1)** — React 18 (не 19) — ради будущей совместимости с VKUI, который планируется подключать позже.
- **2026-06-28 (Фаза 1)** — Установку пакета Prisma и миграции отложили: на Фазе 1 только файл схемы, чтобы скелет запускался без PostgreSQL и без скачивания движков Prisma.
- **2026-06-28 (Фаза 1)** — Бэкенд на ESM + `tsx` для dev (`tsx watch`), сборка через `tsc` — без лишних бандлеров на сервере.
- **2026-06-28 (Фаза 2)** — Для разработки используем уже установленный локальный PostgreSQL 18 (EDB, `localhost:5432`, пользователь `postgres`, база `stockpoisk`); доступ в `.env` (не в гите). На машине есть PgBouncer на 6432 — НЕ используем, подключаемся напрямую к 5432. Первая миграция: `prisma migrate dev --name init`.
- **2026-06-28 (Фаза 3)** — Автоподстановка справочника = поиск по подстроке (`contains`, регистронезависимо), лимит 20; эндпоинты `GET /api/brands`, `GET /api/models`. Jordan ведём отдельным брендом (как в ресейл-культуре и примерах ТЗ), хотя формально это линейка Nike. Seed-справочник идемпотентный (`prisma db seed` через `tsx prisma/seed.ts`).
- **2026-06-28 (Фаза 4, КУРС)** — Расширяем scope за рамки исходного sneaker-MVP: делаем **полный мультикатегорийный продукт с запасом** (обувь, одежда, аксессуары, люкс, коллекционное), цель — заменить чаты реселлеров. Качество > скорости; отступления от ТЗ согласованы с заказчиком. Основание — анализ реального чата (`docs/research/vk_chat_analysis.md`).
- **2026-06-28 (Фаза 4)** — Категории = **таблица-дерево** `Category` (parent/children), а не enum — чтобы админ расширял категории/подкатегории без миграций.
- **2026-06-28 (Фаза 4)** — Размеры: для обуви `sizeUs` + `sizeEu`, для прочего общий `size`; **`sizeRu` убран** (в реальных запросах RU ~0%, US 53% / EU 40%).
- **2026-06-28 (Фаза 4)** — Решаем «разнобой написания» через **алиасы** (`Brand.aliases`, `Model.aliases`); поиск матчит название + алиасы + артикул. Подтверждено данными (nb→New Balance, форсы→Air Force 1, бетон→Bottega).
- **2026-06-28 (Фаза 4)** — В `Listing` добавлены `colorway` (ищут по расцветке: Mocha/Onyx) и `fitting` (примерка — 47% запросов). Jordan, Yeezy, Travis Scott ведём отдельными брендами (ресейл-практика).
- **2026-06-28 (Фаза 4)** — Dev-базу пересоздавали `prisma migrate reset` с явного согласия пользователя (Prisma блокирует это для ИИ-агента); реальных данных не было, только seed.
- **2026-06-28 (Фаза 5)** — Один переиспользуемый компонент `Autocomplete<T>` (fetcher + рендер через пропсы) для брендов и моделей — он же пойдёт в форму продавца и в поиск. Запросы фронта в dev идут через прокси Vite `/api` (без CORS). Пока без VKUI/vk-bridge — обычный React.
- **2026-06-28 (Фаза 6)** — До интеграции vk-bridge сторону продавца ведём от **временного dev-продавца** (`vkId=1`, создаётся на бэке в `getCurrentSellerId()`); фронт про sellerId не знает — заменить на реальную личность при VK-авторизации. Набор полей размера в форме зависит от категории модели (обувь → US/EU, иначе → общий `size`).
- **2026-06-28 (Фаза 7)** — Управление наличием: `PATCH /api/listings/:id` — частичное обновление (только переданные поля), «продано» = `inStock:false`; `DELETE` — удаление. Оба проверяют, что позиция принадлежит текущему продавцу (404 иначе). Редактирование на фронте — инлайн в карточке (`ListingCard`), модель не меняется (для смены — удалить и добавить).
- **2026-06-28 (Фаза 8)** — Поиск: парсер строки вытаскивает размер (явный `Nus`/`Neu`; голое число → EU только в 35–48, чтобы не путать с номерами моделей 4/90/550), остаток — пословный матчинг (AND) по name/aliases/sku/brand. Выдаём только `inStock` и продавцов `approved`. Навигация фронта — вкладки «Поиск / Мой сток». Размер пока матчится точным совпадением строки (диапазон/близость — отдельной задачей).
- **2026-06-28 (Фаза 9)** — Массовый импорт: файл парсит фронт (SheetJS/`xlsx`), на бэк уходят строки JSON; `preview` показывает распознанное/ошибки, `commit` заново сверяет и пишет `createMany` (не доверяем modelId от клиента). Сопоставление модели: точное имя → алиас → подстрока/артикул (в рамках бренда, если распознан). Колонки шаблона: бренд/модель/размер/состояние/цена/фото/комментарий. `xlsx` тяжёлый для бандла — позже lazy-load.
- **2026-06-28 (Фаза 10)** — Профиль продавца: `GET`/`PATCH /api/seller/me` (текущий = dev-продавец до VK-авторизации). Контакт (ВК/TG) один на профиль, привязан ко всем товарам (ТЗ 4.4). Статус модерации меняет только админ.
- **2026-06-28 (Фаза 11)** — Админка под заголовком `x-admin-token` (dev=`dev`, прод — env `ADMIN_TOKEN`); полноценную аутентификацию админа сделаем при деплое. Новые продавцы → `pending`, их сток скрыт в поиске до `approved`. Админ пополняет справочник (бренды/модели с алиасами) — сразу доступно поиску и автоподстановке.
- **2026-06-28 (Фаза 12)** — UI на VKUI v8. vk-bridge даёт «мягкую» личность: заголовок `x-vk-user-id`(+имя), бэкенд `getCurrentSellerId(req)` upsert по vkId (новые → pending); без заголовка — dev-продавец (vk1, approved). Рендер НЕ ждёт vk-bridge дольше 800мс (вне ВК `bridge.send` не резолвится → иначе белый экран). Безопасная проверка подписи launch-параметров и регистрация Mini App — при деплое (нужны app_id/secret).
- **2026-06-28 (Фаза 13)** — Бэкенд переведён с ESM на **CommonJS** (`module`/`moduleResolution: node16`, без `type:module`): иначе прод-запуск `node dist/index.js` падал (ESM требует `.js` в относительных импортах, которые tsc не дописывает). Dev — по-прежнему `tsx`. Это уточняет решение Фазы 1 (ESM).
- **2026-07-03 (план чатов/сделок)** — Принят порядок: A) VK ID OAuth → B) встроенные чаты (привязаны к товару; MVP — поллинг, без вебсокетов) → C) сделки в чате (оффер = размер+цена, торг контр-офферами, принятие = резерв, двустороннее подтверждение = списание + счётчик сделок) → D) рейтинг из реальных метрик (скорость ответа, % завершённых сделок, отзывы). Оплата остаётся вне площадки (позиция «доска объявлений»).
- **2026-07-13 (артикулы + модерация карточек)** — Каждая карточка = модель с заводским артикулом бренда (`Model.sku`, НЕ свой артикул площадки). «Жёсткая база» = модели со статусом `verified` (сид/админ). Продавец, не нашедший карточку, создаёт её сразу как `pending` (не блокируется — иначе не выставит товар), карточка используется и помечается «на модерации»; админ в разделе «Карточки моделей» правит (имя/арт/категория/алиасы/фото) и подтверждает. Не выбрали «жёсткую блокировку до модерации» — это ломает основной сценарий продавца. Реальные SKU — ручной/импортный ввод (инструмент есть), не выдумываем.
- **2026-07-13 (хранение фото)** — Файлы фото храним локально на VPS (named volume `uploads:/app/uploads`), НЕ в S3/облаке: наш масштаб не требует, нет внешних ключей/затрат, бэкап вместе с сервером. Всё загруженное пере-кодируется sharp'ом в WebP ≤1000px (санитизация + вес); имена — random hex (не user-controlled). Переезд на объектное хранилище — если файлов станет много (интерфейс не изменится: меняется только реализация /api/upload/photo).
- **2026-07-12 (формат StockX)** — Витрина переведена на модельные карточки: поиск ведёт к товару (модель), внутри — офферы по размерам с мин. ценой и последней продажей. Убирает дубли объявлений и разнобой названий (цель нормализации через справочник доведена до UI). Старый листинговый /api/search сохранён (аналитика логов, совместимость). Гарант — опциональная строка в сделке (имя/контакт посредника) + системное сообщение; платформа деньги не держит (позиция «доска объявлений» не меняется).
- **2026-07-10 (атрибуция спроса + кириллица в pg_trgm)** — (1) Аналитика не должна врать из-за опечаток: атрибуция лога поиска каскадная (строгий порог 0.3 → мягкий 0.22 только для лога; выдачу мягким не разбавляем), при добавлении модели старые «не нашли» пере-матчатся (90 дней), unmet-запросы кластеризуются (Дайс ≥0.55). (2) **pg_trgm не работает с кириллицей при локали без юникодной классификации** (C-locale/musl-alpine — наш docker-образ postgres:16-alpine!) — все similarity-сравнения делаем через транслит-нормализацию `translate(кир→лат 1:1)` с обеих сторон (TR_FROM/TR_TO в search.ts). Правило: любой новый fuzzy-SQL обязан использовать эту нормализацию.
- **2026-07-09 (рестайл Ice Monochrome)** — Пользователь выбрал (из предложенных вариантов): шрифты **Unbounded+Onest**, палитра **Ice Monochrome** (белый акцент вместо лайма; лайм-эпоха закрыта). Референс — ui.unlumen.com: большой поиск-пилюля с glow на фокусе (`.search-hero`), швейцарский минимализм, микро-анимации без перегруза. Хиро главной уменьшен, страница посвящена поиску. Функциональные цвета (danger/success/warn, VK-синий) не тронуты.
- **2026-07-08 (шрифты — кириллица обязательна)** — UI полностью русский, поэтому дисплейный и текстовый шрифты ДОЛЖНЫ поддерживать кириллицу. Anton/Epilogue (из первого редизайна) её не имеют → откат на **Oswald** (дисплей) + **Inter** (текст), оба с кириллицей. Правило на будущее: перед выбором Google-фонта проверять наличие cyrillic-сабсета (`node_modules/@fontsource/<f>/files/*cyrillic*`). Единый заголовок — класс `.page-title`.
- **2026-07-07 (редизайн, ui-ux-pro-max)** — Дизайн ведём через скилл `ui-ux-pro-max`: паттерн Marketplace + стиль Modern Dark. Шрифты Anton (дисплей) + Epilogue (текст) self-hosted. Фирменный лайм-акцент СОХРАНЁН вопреки сгенерированной палитре (правило consistency — узнаваемость бренда важнее), из движка взяты: глубина/элевация, стекло на липких панелях, атмосферное свечение, кинематографичность, набор UX-правил (a11y, навигация, формы, тач). Класс-контракт theme.css не меняли — редизайн через токены/классы, компоненты не переписывали. Плотность/variance по дефолту (6/6).
- **2026-07-06 (аналитика спроса, PRO)** — Ключевая ценность и монетизация площадки: аналитика из first-party данных (запросы «Ищу», логи поиска, сделки, сток), которой у отдельного реселлера нет. Фаза 1 — дашборд спроса: дефицит (спрос vs предложение — что закупать), что ищут, что продаётся, «ищут-но-не-нашли». Логируем поиск с самого начала (`SearchLog`), т.к. спрос копится быстрее сделок; ценовую историю/скорость/скоринг «что закупать» включаем позже по мере объёма сделок (честно про холодный старт, не врать выборкой). Флагман (позже) — скоринг «купи это»: спрос↑ + предложение↓ + быстрая продажа + маржа. Пейволл PRO подключим в фазе монетизации.
- **2026-07-06 (фото каталога)** — Фото привязано к модели (`Model.imageUrl`), а не к каждому объявлению — как на StockX/GOAT: продавец указывает размер+цену, фото подставляется автоматически. Приоритет: фото объявления → каталожное фото модели → буква-заглушка. Наполнение — вариант A (куратор+сид): админ/автор новой модели задаёт URL; авто-поиск по image-API (B) и загрузка в объектное хранилище (C) отложены (платно/инфраструктура/копирайт). Сид фейковыми URL не делаем — плейсхолдеры хуже чистой буквы-заглушки; реальные фото заливает куратор (источник — решение владельца по праву/качеству).
- **2026-07-06 (нечёткий поиск)** — Релевантный поиск на PostgreSQL `pg_trgm` (триграммы), без Elasticsearch — достаточно для наших объёмов и без лишней инфраструктуры. Скоринг моделей по единому «документу» (бренд+модель+алиасы+артикул): `word_similarity` (устойчивость к опечаткам) + бонусы за подстроку/префикс/точный алиас. Выдача ранжируется по релевантности (бакеты 0.1), внутри бакета — по выбранной сортировке. Порог отсечения `word_similarity > 0.3`, иначе — точная подстрока. Сокращения (af1, форсы) закрываются алиасами в справочнике. Миграция `search_trgm` включает расширение + GIN-индексы.
- **2026-07-04 (свои модели)** — Продавец может добавить модель/бренд, которых нет в справочнике, прямо из формы стока (`POST /api/models`, любой вошедший) — иначе позицию не добавить. Дубликаты гасятся регистронезависимым поиском, бренд заводится автоматически. Риск замусоривания принят (объёмы малые); при росте — модерация/слияние моделей админом.
- **2026-07-03 (доска запросов)** — Запрос строго по модели из справочника (точный матчинг вместо разбора текста). Матч = модель + размер (равенство с любым из size-полей) + бюджет. Отклик продавца = существующий механизм чата+оффера (никакой параллельной переписки), одна позиция — один отклик на запрос. Лимит 10 активных запросов на пользователя. Уведомления о подходящих запросах — позже (пока пассивная лента с «у тебя подходящих: N»).
- **2026-07-03 (мобильная навигация)** — На мобиле нижний таб-бар из 5 разделов (Поиск/Запросы/Чаты/Сток/Профиль), иконки — инлайн-SVG (без icon-библиотек); Главная по тапу на лого; Админ — только на десктопе.
- **2026-07-03 (тест-вход)** — Включён по умолчанию (выключение — `ALLOW_TEST_LOGIN=0` при запуске VK ID): на проде тестовый период, флаг забывался.
- **2026-07-03 (рейтинг)** — Без синтетической «единой цифры»: показываем честные метрики — среднюю оценку отзывов (1–5), число завершённых сделок, % доведённых до конца (только при ≥3 закрытых), медиану скорости первого ответа, стаж на площадке. Отзыв — только покупатель, только по завершённой сделке, один на сделку (накрутка затруднена: нужна реальная сделка). Метрики считаются на лету (объёмы малые), кэширование — когда понадобится.
- **2026-07-03 (сделки)** — Оффер = сообщение в чате (`kind=offer`, цена; позиция определяется диалогом). Один активный оффер на чат (новый суперсидит). Принятие (только второй стороной) = `Deal open` + `Listing.reserved` (скрыт из поиска, правки запрещены). Завершение — **двустороннее подтверждение** → `completed` + `inStock=false`; отмена любой стороной возвращает в продажу. История — системными сообщениями в ленте. Счётчики сделок для рейтинга считаются из Deal (фаза D).
- **2026-07-03 (чаты)** — Диалог привязан к паре товар+покупатель (`@@unique`), продавец — владелец товара; писать по своему товару нельзя. Обновление — поллингом (актив. чат 4с, список 10с, бейдж 15с), вебсокеты отложены сознательно (VPS 2ГБ, простота). Прочтение: GET сообщений помечает входящие `readAt`. «Написать продавцу»: с входом — внутренний чат, без входа — внешний контакт (фоллбек до VK ID).
- **2026-07-03 (VK ID, блокер)** — Подключение VK ID требует бизнес-аккаунта VK ID у владельца — пока не оформлен, вход на проде не активен (код готов; dev-режим работает локально). Оформление — действие пользователя.
