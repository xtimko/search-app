## Сделано (VK ID — корректная интеграция OAuth 2.1)

- [x] **Реальный вход через VK ID приведён к спецификации id.vk.ru** (app 54693313). Сверено с офиц. доками (access/refresh/id-token, api-description). Исправлены баги, ломавшие прод-вход: (1) **`trustProxy: true`** в Fastify — за nginx `req.protocol` был `http`, redirect_uri уходил бы как `http://…` и VK его отклонял; (2) **`state`** удлинён до 43 симв. (`randomBytes(32)`) — VK требует ≥32, было 22; (3) **`code_challenge_method`** `s256`→`S256` (регистр важен). Приведено к актуальной схеме: домены `id.vk.com`→`id.vk.ru` (authorize/oauth2/auth/user_info); обмен кода — через **`service_token`** (VK ID использует PKCE + service_token для конфиденциальных, а не `client_secret`); **`VK_REDIRECT_URI`** через env (точное совпадение с кабинетом надёжнее вывода из заголовков за прокси). Осознанно: refresh_token/id_token НЕ храним (сессия самодостаточна — наша httpOnly HMAC-cookie 30 дней; id-token несёт лишь маскированные данные, полный профиль берём из `user_info`); VK-токены после входа не нужны (VK API не дёргаем). Архитектура — серверный флоу, НЕ SDK-виджет OneTap (секрет на сервере, токены в браузер не попадают). Тестовый вход выключен по умолчанию (`ALLOW_TEST_LOGIN=1` — аварийный), в проде только VK ID. Проверено локально: `/api/auth/vk/login` → корректный редирект на `id.vk.ru/authorize` (client_id 54693313, redirect_uri точный, state 43 симв., S256); test-login → 403; сборка бэка чистая. Живой вход через VK проверяется на проде (нужны env + redirect URL в кабинете — см. DEPLOY §7). Действие пользователя: добавить в кабинете доверенный redirect `https://search-app.ru/api/auth/vk/callback` и заполнить `.env`.
